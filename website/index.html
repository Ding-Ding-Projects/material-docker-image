    AuthenticatorUnverifiedauthenticator

    Partly delivered: the Tools page has an Authenticator section with My accounts and App locks. My accounts is a general authenticator: it adds accounts from an otpauth link (parameters honoured) or by hand, shows each account's code grouped for reading with a seconds countdown and the next code, copies a code, renames, reorders and deletes with confirmation, searches, protects the whole list for the Windows account with DPAPI, and exports or imports an AES-256-GCM backup under a passphrase. Grouping, a clock-skew warning and a super-confirmed secrets export are not built, and nothing has been driven in the built window.

    Remaining actions

    Element LocksUnverifiedelement-locks

    Partly delivered: every settings row that holds a value has a lock button, and every button, switch, option, drop-down, text field and slider on every page has Lock this control on its right-click menu, with a stable id (its automation id, otherwise its page, kind, English name and position among identical elements). Each lock chooses one of eight policies: confirm only, PIN, password, authenticator app, PIN plus password, password plus authenticator, PIN plus authenticator, or password plus PIN plus authenticator. PINs and passwords are stored as salted PBKDF2-SHA256 hashes, the authenticator secret is protected with Windows DPAPI, attempts are backoff-limited and persist, and single-use recovery codes are made at setup. Each lock also chooses how long an unlock lasts (this action only, 5 minutes, 1 hour, or until the app closes) and closes again by itself, including at the next launch. Settings has a Locks manager listing every lock with search, filters, export, unlock, lock again, change policy and single or bulk removal. A locked control is disabled, locks persist and are recorded in history without credentials, and import, reset, palette controls and the accessibility menu respect them. The logic is covered by focused checks that were seen failing first. Tabs and tab groups (the pinned region, the open region and the navigation rail) can be locked from their context menus and refuse switching, closing, moving and pinning; every appearance value, each colour role, saved presets and each property of a customized element has its own lock that holds against editing, presets, paste, undo, import and reset; clicking a locked control opens its unlock prompt instead of doing nothing; locked tabs and commands are labelled in the palette, the tab search and the New tab catalog (with an optional setting to hide them, announced in each list); locked tabs are kept out of bulk closes; and the unlock prompt has a PIN keypad that shares the one validator and attempt budget with typing. These rules are covered by focused checks that were seen failing first. Not built: user-made tab groups, a tab-group search and an all-windows tab search, a keypad in the PIN wizard, and an unlock prompt anchored beside the control (it is the shared overlay dialog). Nothing has been driven in the built window.

      Advanced image builds
      

      The Build workspace keeps the Dockerfile editor beside the selected local context. Advanced controls expand in place and use structured Docker CLI arguments.
      

      Outputs
      

      • Load into local engine is the default. This editor accepts one platform for a local load.
      

      • Push to registry accepts multiple tags and platforms and requires confirmation naming the destination tags. Docker retains ownership of registry authentication.
      

      • Export OCI archive writes to a selected local archive path. The parent directory must exist, and replacing an existing archive requires confirmation. Exporter availability depends on the installed builder.
      

      The Image tag field accepts comma-separated or line-separated tags. Labels use one key=value per line. Label keys support namespace punctuation; values retain spaces exactly. The application does not shell-interpret values.
      

      Cache
      

      Cache import and export accept one BuildKit specification per line, such as type=local,src=C:/cache or type=registry,ref=registry.example/team/cache. The installed builder decides which backends it supports. Export is a write operation and requires confirmation. Do not place credentials in these fields.
      

      BuildKit secret files
      

      Add a secret row, choose an existing local file, and enter the identifier used by the Dockerfile's RUN --mount=type=secret instruction. The application passes the selected path to BuildKit without reading or persisting the file's contents. Selections remain in the current window only. The Dockerfile itself must avoid printing secrets or copying them into an image.
      

      Check before building
      

      Check Dockerfile with BuildKit invokes the installed builder's actual --check route against the saved Dockerfile. Unsupported builder versions report their real error. A check is distinct from a successful build, image load, registry publication or container health result.
      

      BuildKit timeline
      

      Builds run with --progress=plain and the output is parsed into a timeline: one row per step with its stage, status (running, cached, done, failed, cancelled), a duration bar scaled to the longest step and the step's own log. Statistics tiles show total time, cached steps, step count and the resulting digest. Click a step to filter the log to it. A failure shows the "failed to solve" summary as a banner.
      

      After a successful build the metadata file is read to show the image digest, config digest, names and attestations, with Run, Push and Copy digest. Recent builds combines this session's builds with docker buildx history ls when the installed Buildx supports it, and says so when it does not.
      

      More options
      

      • Platform chips for common platforms plus any other platform; a local load refuses more than one.
      

      • Mode: Build, Check, Outline (build arguments and secrets the Dockerfile uses) and Targets (stages you can build, with Use as target).
      

      • Export files writes the result to a local folder and asks before writing into a non-empty one.
      

      • Named build contexts, SSH agent forwarding, environment-variable secrets (the value is never read or shown), SBOM and provenance attestations, annotations, RUN network mode (host needs the network.host entitlement), shared memory size, ulimits and extra hosts.
      

      • A live command preview with copy shows exactly what will run, or why the input is invalid.
      

      Bake
      

      The Bake destination opens a folder (Bake reads its default files such as docker-bake.hcl and compose.yaml) or a specific file. It lists groups and targets from docker buildx bake --list=targets and the resolved definition of each from --print. Select targets or a group, add --set overrides, choose Load, Push or the file's own outputs, and build with the same timeline as Build. Push asks first; Load refuses multi-platform targets unless you override the platform.

      Appearance and motion
      

      Appearance editor
      

      Settings > Appearance opens the appearance editor with a live preview. Every change applies immediately, is saved, and is recorded in local history; Undo and Redo keep the last 100 changes.
      

      • Presets: seven built-in presets plus your own. Apply, save as, rename, delete, export to a file and import from one (validated, 64 KiB limit, unknown fields rejected), and copy or paste a style.
      

      • Colour: theme (light, dark, system), seed colour, chroma, surface tint and per-role overrides. The colour picker has a saturation and value field usable with the keyboard, hue and alpha sliders, and editable values in HEX, RGB, HSL, HSV, HWB, CMYK, OKLab and OKLCH with copy buttons. Contrast badges show the WCAG ratio against each role's partner; colours outside sRGB are brought back into range with a warning.
      

      • Shape and density: corner radius scale and density, which change buttons, fields, chips, menus, cards and dialogs.
      

      • Typography: interface and code fonts from a searchable list of installed fonts, each drawn in its own font, plus heading weight.
      

      • Effects: elevation strength and an optional rainbow accent that settles on the saved colour when motion is off.

      Per-element customization
      

      Any element can be customized on its own, beyond the shared colour roles. Open the editor from Customize this element… (right-click menu of the page area, or the button in the Edit appearance panel), from the command palette (Customize the focused element…), or with Pick an element to customize…, which turns the pointer into a cross and uses the next click without pressing what is under it (Escape cancels).
      

      • What it edits: background colour and text colour (the same infinite picker, with HEX, RGB and HSL), corner radius (0 to 48), font size (8 to 40) and weight (300 to 700), padding (0 to 40) and visibility (hidden elements keep their space). Each property is switched on separately and previews live on the element itself. A contrast warning appears when text and background are both set and fall under 3:1.
      

      • Identity: an element is found again by its path from the window (type, name where it has one, position among siblings of the same type), for example MainWindow/Grid/Border[2]/Button#btn.build. The key is stable across restarts and page rebuilds while the layout around the element is unchanged; if the layout changes, the override no longer matches and is listed under Overrides until reset.
      

      • Persistence: overrides live in element-appearance.json in the data folder (strict format, 256 KiB and 200-element limits, written atomically) and are recorded in local history when the editor closes. An unreadable file is reported and never overwritten.
      

      • Overrides list: the Overrides tab lists every override with a plain-words description, a search with its own regular expression builder, Reset per element and Reset all customized elements (confirmed). Reset element and Revert changes work from the Element tab.
      

      • Locks: a property whose appearance setting is locked in Settings (colour roles, corner radius, font size, density for padding) is shown read-only in the editor, with the same note as a locked setting row.
      

      • Applying: overrides are applied to live elements when they change and to each element as it loads; removing an override restores the element's original value, binding or resource reference.
      

      Not built: per-element overrides are not yet part of appearance presets, export or Undo, only a subset of the property types the shared contract lists (no italic, underline, shadow, spacing or alignment), and the editor has not been driven in the built window.
      

      Motion
      

      Motion follows Material 3 easing and duration tokens. Choose Off, Reduced, Standard or Expressive and a speed from 0.5x to 2x.
      

      • Moving between rail destinations slides in the direction of the rail; other page changes fade through. Tabs slide.

      • The rail indicator grows from its centre, buttons respond to presses, switches slide and expanders reveal their content.
      

      • Table rows fade in on first load.
      

      Reduced motion, Low stimulation, the Windows animation setting and capture mode always win over the saved level. Every animation ends on the element's normal state, so an interrupted animation never leaves anything hidden or moved.

      Build companion
      

      MaterialDockerImageBuild.exe is a small, separate Windows window for people who prefer a button to a command prompt. It does not replace build.bat or build-installer.bat; it runs them. Every release attaches it beside the installer.
      

      What it does
      

      • Finds the repository. It uses --repo <path> when given, otherwise walks up from its own folder looking for build.bat, otherwise asks you to choose the folder. A --repo path that is relative, contains characters cmd.exe would interpret (", %, ^, !, <, >, |) or has no build.bat is refused.
      

      • Setup check. Lists build.bat, build-installer.bat, download-dependencies.bat, .tools/dotnet-path.txt, .tools/node-path.txt and out/publish/MaterialDockerImage.exe. The three batch files are required. The two .tools files are created by the first build: the batch files download and verify the pinned .NET SDK and Node.js themselves (see build/dependencies.json), without administrator rights. The companion only reports and explains this; it never elevates and never installs anything itself.
      

      • Build. Runs the repository's build.bat, with -Version x.y.z when a version is entered.
      

      • Build and run. Runs build.bat, then starts out/publish/MaterialDockerImage.exe only if the build exited with code 0 and the file exists.
      

      • Build installer. Runs build-installer.bat -Version x.y.z. The version is required. The installer is unsigned, so Windows may show an unknown-publisher warning.
      

      • Live progress. Standard output and standard error stream into the log view while the build runs (standard error lines are prefixed [err]). A phase label (starting, preparing dependencies, compiling and publishing, packaging installer) is inferred from the output text and is a hint only; the progress bar is indeterminate while running.
      

      • Real result. The window shows elapsed time, the real exit code and a state chip: Succeeded, Failed, Cancelled or Could not start. Success is reported only for exit code 0 without cancellation.
      

      • Cancel (button or Esc) kills the whole process tree. Copy log (button or Ctrl+Shift+C) copies the complete log.
      

      • Language. The language button cycles English, Cantonese and bilingual labels from a small local string table. Build output stays as the tools print it.
      

      Keyboard: Ctrl+B build, Ctrl+R build and run, Ctrl+I installer, Esc cancel, Ctrl+Shift+C copy log. Every control has an automation name; the version field has help text; the state chip is a polite live region.
      

      How commands are run
      

      Each batch file is started as cmd.exe /d /c ""<repo>\build.bat" -Version 1.2.3" with the repository as the working directory. The version must match ^\d+\.\d+\.\d+$ (ASCII digits only, no trailing text). Nothing the user types reaches a command line unvalidated. The logic lives in src/BuildCompanion/Logic/ (BuildPlan, ArgumentValidation, BuildRunner, RunStates, PhaseTracker, RepoLocator, SetupCheck, CompanionStrings) and has no WPF dependency, so the UI-state test project compiles it directly.

      Container configuration
      

      Select an image from a refreshed inventory, then choose Run. The dialog remains bound to the engine context and generation that produced the selection. A changed context invalidates the selection.
      

      Ports and storage
      

      The basic port field uses host:container, optionally followed by /tcp or /udp, and binds to loopback. Additional port rows expose the bind address, host port, container port and protocol independently. An all-interface address publishes more broadly and must be chosen intentionally.
      

      Additional mount rows distinguish named volumes from bind paths, provide a container destination, and default to read-only. Browse chooses a folder on this computer. A bind source belongs to the selected engine host, which may be remote; the application does not incorrectly require a remote path to exist locally. Confirm that the engine can access any chosen source.
      

      Execution and environment
      

      Command arguments are a JSON string array, for example ["/bin/echo", "hello world"]. Each string remains a separate argument after the image operand. A shell inside a container runs only if explicitly selected as the container executable; the application does not invoke a host shell for Docker operations.
      

      Environment entries use NAME=value, one per line. Everything after the first equals sign is preserved, including trailing spaces. Enter non-secret values only. Entrypoint, container user and working directory can be overridden independently; blank values retain the image behavior where Docker permits it.
      

      Resources and security
      

      CPU and memory limits, restart policy, read-only root filesystem and prevention of new privileges are exposed as real controls. The engine validates their final compatibility with the chosen image and host. Preventing new privileges is enabled in this editor by default and may affect images that rely on set-user-ID behavior.
      

      No privileged mode or host networking is enabled by this dialog. Interactive terminals open from Containers › Exec › Open terminal as docker exec -it <container> <shell> in a separate console window. By default Windows chooses the console through the default terminal application; Settings › Engine › Open terminals in a classic console window starts conhost.exe directly instead, which always opens its own window next to the app (verified on a desktop host with an alpine container, see evidence/interactive-2026-11/receipt.json). Health checks, device mappings and GPU access are described below. Compose remains available for project configuration, but does not constitute acceptance evidence for absent graphical controls.
      

      Health checks, devices and GPUs
      

      Restart and health holds the health-check fields. Each field maps to one flag and is validated before Run is enabled: Health command (--health-cmd, run through the container shell), Interval (--health-interval), Timeout (--health-timeout), Retries (--health-retries, a positive whole number), Start period (--health-start-period), Start interval (--health-start-interval, needs Docker Engine 25 or later) and Disable the image health check (--no-healthcheck). Durations use Go syntax such as 30s, 1m30s or 500ms, must be at least 1ms, and zero is refused. Disabling the check cannot be combined with a command or timing option.
      

      Resources holds GPU and device access. GPUs accepts all, a positive count, or device IDs such as device=0,1, with optional capabilities such as compute and utility; capabilities are always sent as one quoted field because the engine rejects an unquoted list. Device rows map a host path to a container path with permissions that are a non-repeating subset of r, w and m, and two rows cannot claim the same container path. Device cgroup rules take one rule per line, for example c 189:* rwm. Device paths belong to the engine host, which may not be this computer. A warning appears whenever GPUs, devices or rules are set.
      

      The Containers inspector Overview lists the configured health check, the live status, the failing streak and the last probe outputs. While a running container with a health check is open on Overview, the inspector re-reads it every five seconds and redraws only when the status, streak or latest probe changes. Below that, Devices and GPUs lists configured devices, cgroup rules and the engine DeviceRequests. If the engine reports a start error that mentions a missing device driver, the inspector says the engine has no GPU support; a failed Run says the same instead of leaving only the raw engine text.

      Engine contexts and Swarm
      

      Contexts
      

      Contexts shows every Docker engine context as a card with its description, endpoint, transport, whether it is the CLI's current context and whether this window uses it. Every context is probed in parallel (ten-second limit) and shows its engine version, platform and API version, or the error.
      

      • Use in this window switches only this window and records the change in local history. The app never runs docker context use.
      

      • Create offers endpoint presets for named pipe, Unix socket, TCP and SSH, TLS certificate pickers and a live command preview.
      

      • Update, Inspect (sanitized), Export (with a warning about key material) and Import are available. Remove asks first and refuses the default context and the one this window uses.
      

      • Plugins lists the CLI plugins, failed plugins and CLI warnings, with search. A note shows where the CLI configuration lives and warns when DOCKER_HOST or DOCKER_CONTEXT is set.
      

      Swarm
      

      Swarm reads the engine's swarm state and shows what fits it.
      

      • Not in a swarm: Init (optional advertise address) and Join (token in a password field) with confirmation.
      

      • Workers, pending or locked nodes: an explanation and Leave. Leave asks first; forced leave needs the super confirmation.
      

      • Managers: a statistics strip and tabs:
      

        - Services: replica chips, a task timeline from docker service ps, logs with follow, scale, update image, rollback, remove and a create form with ports, environment and constraints. Environment values are masked in the preview and never stored.
      

        - Stacks: deploy from a Compose file, list services and remove with a super confirmation listing them.
      

        - Nodes: availability (active, pause, drain), promote, demote and inspect.
      

        - Secrets: create from a typed value sent on standard input or from a file the CLI reads; inspect shows metadata only.
      

        - Configs: create from a file, view decoded content, inspect and remove.
      

      Volume backup, restore and clone
      

      In Storage, a volume can be backed up to a .tar.gz archive with a short-lived helper container that has no network. Containers using the volume can be stopped for the backup and are always started again afterwards. Restore writes an archive into an existing or new volume; replacing current contents needs the super confirmation. Clone copies a volume into a new one without using a host folder, so it also works with remote engines.

      Diagnostics and safety
      

      Diagnostics records actual CLI and engine responses. Separate read-only inspection from a smoke test that creates resources. Controlled smoke tests use unique owned names, labels, and exact teardown targets. Failed teardown remains an unsuccessful overall result.
      

      Commands are invoked without a shell. User values become individual process arguments. Docker context selection is per command. Existing Docker credential helpers retain ownership of authentication; credentials must not enter command previews, application logs or diagnostic exports.
      

      Output is bounded to protect memory. A truncated output buffer must be identified as truncated, never described as complete. Cancellation can stop the CLI before the engine has reconciled its work. Refresh state and inspect the resource rather than assuming rollback.
      

      Only run trusted build projects. Docker engine access carries substantial authority over its host. This application does not make an untrusted Dockerfile, image, bind mount or Compose project safe.

      Dockerfile Creator
      

      The Creator builds a Dockerfile from structured steps, shows the exact text as you work, and checks it against common best practices.
      

      Start
      

      Choose a starter: Node.js service, Python with pip, Python with uv, .NET (ASP.NET), Go static binary, Java (Maven build with a JRE runtime), Rust, static site served by an unprivileged nginx, or Blank. Each starter states what it creates. Applying a starter replaces the current draft; the previous draft is recorded in local history first so it can be restored from Activity. You can also import an existing Dockerfile: instructions become structured steps, and anything the editor cannot represent is kept as a raw card with Edit as text.
      

      The Detected project card inspects a folder like docker init: Node (npm, yarn, pnpm), Python (pip, uv, poetry; FastAPI, Flask, Django), Go, .NET, Rust, Java (Maven, Gradle) and static sites, plus existing Dockerfile, Compose and .dockerignore files. Each finding shows its evidence file. Apply suggestion replaces the draft (the old draft goes to local history first), and Write to folder asks before replacing any file.
      

      Stages
      

      The left column lists the stages. Add, rename, duplicate, delete (with confirmation), reorder, or set a stage as the build target. Each stage has a base image (editable, with common images suggested), a name and an optional platform.
      

      Steps
      

      Each instruction is a card with its keyword, a summary and a hint. Expand a card to edit it with a form specific to its kind:
      

      • ARG, ENV and LABEL as name and value rows.
      

      • COPY with sources, destination, --from stage, --chown, --chmod (numeric or symbolic), --link, --parents, repeated --exclude and an inline file written as a heredoc.
      

      • ADD from a local path, a URL or a Git repository, with --checksum and --keep-git-dir.
      

      • RUN as shell or exec form or as a heredoc script with an interpreter, plus a mounts editor for all five mount types (bind, cache, tmpfs, secret, ssh) with every option, cache presets for apt, npm, pip, uv, Go, Cargo, NuGet, Maven and Gradle, and --network and --security (insecure warns about the entitlement it needs).
      

      • Global build arguments before the first stage, one-click TARGETPLATFORM and BUILDPLATFORM helpers, Build on BUILDPLATFORM for cross-compilation, and the # syntax, # escape and # check directives.
      

      • USER, WORKDIR, EXPOSE (port and protocol), VOLUME, STOPSIGNAL, SHELL, ONBUILD and comments.
      

      • ENTRYPOINT and CMD in exec form with one field per argument.
      

      • HEALTHCHECK with command, interval, timeout, retries and start period.
      

      Fields are validated as you type. Move steps with the arrow buttons or Alt+Up and Alt+Down; duplicate or delete them from the card or its context menu. Add instruction opens a searchable list, and quick-add chips insert a cached RUN, a HEALTHCHECK, a non-root USER or an EXPOSE.
      

      Live, editable source
      

      The source on the right is an editor, not just a preview. Type in it and, 300 ms after you stop (or when it loses focus), the stages and cards are rebuilt from your text without moving the caret or scroll position. Editing a card replaces only that instruction's lines, so your comments, blank lines, spacing and CRLF line endings are kept. Opening a card selects its lines in the source; moving the caret selects the matching stage and outlines its card. Lines the model cannot represent become raw cards with Edit as text, and parse notes appear in Checks with a link to the line. Adding, removing or moving steps and editing directives still re-render the whole file.
      

      The source has search, a coloured read-only view, Copy as build command (docker buildx build with target, entitlements, secret ids and SSH, never secret values), a .dockerignore tab with language presets and a live check against a context folder, and a compose.yaml tab when one is generated.
      

      Checks
      

      The Checks panel reports, among others: an unpinned base image, a final stage that runs as root, no health check, apt-get update without an install in the same step, missing --no-install-recommends or cleanup, ADD used for local files, shell-form CMD or ENTRYPOINT, a web service without EXPOSE, COPY . . before dependency installation, secret-looking ARG or ENV names, duplicate stage names, COPY --from pointing to an unknown or later stage, a relative WORKDIR, and several CMD instructions. Rules DF100 to DF124 add mount, heredoc, platform and syntax-version checks; DF116 offers to add or upgrade the # syntax header when a feature needs a newer Dockerfile frontend. Findings that match a BuildKit check show its name, and # check=skip= hides them here too. Most findings have a Fix button; fixes that need a value (such as a tag or digest to pin) ask for it first.
      

      Saving and building
      

      Undo and Redo keep the last 200 changes. The draft is saved automatically in the application data folder and recorded in local history after two seconds without changes. Save as writes a Dockerfile you choose. Open in Build sends the text to the Build destination as an unsaved draft together with the selected target stage, so you can review it and build.

      Editor suggestions and value pickers
      

      The Build Dockerfile editor, the Creator's editable source and the Compose file editor share one suggestion engine.
      

      Suggestions
      

      Suggestions open after a short pause in typing or after a trigger character (-, =, $, {, :, /, ,, # or a space), and always with Ctrl+Space. Use Up, Down, Page Up and Page Down to move, Tab or Enter to accept and Esc to close. Matching characters are shown in bold, every item has an icon for its kind, and the side pane shows its description, an example and the minimum # syntax version it needs. Accepted text goes through the editor, so Ctrl+Z undoes it.
      

      In a Dockerfile, suggestions follow what is at the cursor:
      

      • At the start of a line: every instruction, parser directives at the top of the file, and snippets such as a cached package install or a health check.
      

      • After an instruction: the flags that instruction accepts, without the ones already used.
      

      • Inside --mount=: the mount types, the options valid for the chosen type, and their values.
      

      • --from= and FROM: stages defined earlier in the file.
      

      • After $ or ${: the build arguments and environment variables in scope, including the platform arguments. A global argument used inside a stage without being declared there is marked.
      

      • After FROM: your local images and a clearly labelled list of popular official images; after :, the tags of local images.
      

      • After COPY and ADD: names from the build context (up to 500), skipping entries excluded by .dockerignore, symbolic links and names that look like secrets. File contents are never read.
      

      • Values for EXPOSE, STOPSIGNAL, SHELL, USER, HEALTHCHECK and OCI label keys.
      

      A hint line under the cursor shows the instruction's full form, and resting the mouse on a keyword, flag, mount option, directive or Compose key for half a second shows its documentation. Items that need a newer Dockerfile frontend than the file declares carry a badge such as "1.4+"; after accepting one, Ctrl+Enter adds or upgrades the # syntax=docker/dockerfile:1 header.
      

      In Compose files, keys are suggested by indentation (top level, service, build, health check, depends_on, develop.watch, deploy, logging, ports and volumes in long form, and the top-level volumes, networks, secrets and configs), together with values and the names of your services, volumes, networks, secrets, configs and profiles.
      

      Value pickers
      

      When the value at the cursor has a known type, the list offers a picker and Ctrl+Shift+Space opens it directly. Tab moves inside a picker, Enter applies the value and Esc returns to the editor with the cursor where it was.
      

      • Path: a file or folder dialog that opens at the build context or Compose folder and inserts a relative path with forward slashes. Paths outside the build context are refused for COPY and ADD, with an explanation.
      

      • Colour: the colour picker from the appearance editor, keeping the original notation.
      

      • Port: container port and protocol, plus host port and address for Compose, with warnings for privileged ports and host ports already published on the engine.
      

      • Duration: presets and a number with a unit, for health check timings.
      

      • Permissions: an owner, group and other grid for --chmod, producing octal or symbolic form.
      

      • User: common users (root, node, nobody, 65532) and a numeric uid:gid editor.
      

      • Platform: chips for common platforms.
      

      • Image: a searchable list of local images and tags, with Pin digest using the image's real repository digest (disabled when there is none).
      

      • Fixed choices such as signals, restart policies, mount types and sharing modes: chips.
      

      • Secret-looking variables: Use a build secret instead rewrites the line to RUN --mount=type=secret,id=…,env=NAME. The value is dropped and never shown.
      

      Settings and commands
      

      Settings > Engine has Show suggestions while typing (on by default). Ctrl+Space and Ctrl+Shift+Space always work. The command palette has Trigger suggestions, Pick value at caret and a switch for the setting.
      

      Status
      

      Built and covered by UI-state checks for every suggestion context, scoping, fuzzy ranking, version badges, Compose indentation and each picker's value type. Popup placement, focus behaviour and the pickers have not yet been exercised interactively on Windows. Ctrl+Space can clash with the input-method toggle in some Chinese input setups; the palette command works there.

      Local history
      

      Every meaningful change is recorded in a local version history so it can be reviewed, compared and restored.
      

      Where it lives
      

      The history is a Git repository in the application's own data folder:
      

      %LOCALAPPDATA%\DingDingProjects\MaterialDockerImage\history. It is never created inside your project folders, and nothing in it is sent anywhere.
      

      What is recorded
      

      • Settings changes (the complete settings file at each change).
      

      • Dockerfile and Compose saves, and Dockerfile Creator drafts, with their content.
      

      • Operations: the label, result and engine context of each build, run, removal or prune. Command arguments are not recorded, so environment values never enter the history.
      

      • Discarded drafts when the window closes with unsaved work.
      

      Passwords and BuildKit secret file contents are never recorded.
      

      Using it
      

      The Activity destination lists revisions with time, action and summary. Filter by action, by date range and by text (with the regular expression builder). Select a revision to see its diff.
      

      • Restore writes the chosen file content as a new revision. History is append-only: a restore never rewrites earlier revisions, and a restore can itself be restored.
      

      • Label names a revision so it is easy to find later.
      

      • Export writes the selected or visible revisions to a ZIP file with a JSON index and one patch per revision.
      

      If the history cannot be opened or written, the Activity destination says so. A history failure never fails the operation you were running.

      Minecraft servers
      

      The Minecraft destination creates and runs Minecraft servers as containers using the community itzg/minecraft-server (Java) and itzg/minecraft-bedrock-server (Bedrock) images. It lists only containers and volumes labelled material-docker-image.minecraft, so your other containers are never touched.
      

      Create a server
      

      A six-step wizard with Back and Next:
      

      1. Where: the local engine or an SSH engine context.
      

      2. Edition and version: latest, snapshot or preview, or a typed version. Refresh versions downloads the official version list through a pinned helper container.
      

      3. Server type: Vanilla, Paper, Purpur, Fabric, Forge, NeoForge and the other types the image supports, or a custom server jar.
      

      4. Resources and network: memory, port and listen address (127.0.0.1 by default, with a warning for 0.0.0.0). Bedrock uses 19132/udp.
      

      5. Game settings: typed controls for server.properties, operators, whitelist, and Modrinth or Spigot plugins where the type supports them.
      

      6. Review: the exact command preview and the Minecraft EULA. The server is only told the EULA is accepted when you tick the box.
      

      The RCON password is passed in a temporary environment file that is deleted straight away, and is shown as dots in the preview. The Java runtime image tag is chosen from the version.
      

      Manage a server
      

      • Overview: live statistics, uptime and the connect address.
      

      • Console: follows the server log with search and command history, and sends commands through RCON (Bedrock through the image's command helper).
      

      • Players: online players, operators and whitelist, with op, deop, whitelist and kick.
      

      • Properties: shows the differences, then recreates the container with the new settings. The old container is kept until the new one starts, and the world volume and password are kept.

      Engine binding
      

      • Engine: System.Text.RegularExpressions on .NET 10, regular expression dialect ".NET". The builder never silently substitutes another engine.
      

      • The non-backtracking engine is used whenever the pattern allows it. Patterns that need backtracking (lookarounds, backreferences, atomic groups, conditionals, balancing groups, RightToLeft) run on the backtracking engine with a 250 ms limit per match.
      

      • Flags offered (8): IgnoreCase, Multiline, Singleline, IgnorePatternWhitespace, ExplicitCapture, CultureInvariant, RightToLeft, NonBacktracking. RightToLeft uses the backtracking engine. NonBacktracking means "require the linear-time engine": a pattern that needs backtracking is reported as unsupported instead of falling back, and combining it with RightToLeft is refused.
      

      • Limits: 4096 pattern characters, 64 KiB sample, 2000 highlighted matches, 2 s per test, 256 KiB replace output, 2000 split pieces, 200 test cases, 200 saved patterns, 50 remembered experiments (1 MiB, 16 KiB sample each). Folder search: 2 MiB per file by default (16 MiB ceiling), 5000 files (20000 ceiling), 1000 results (5000 ceiling), 200 matches per file, 128 MiB read in total, 15 s; replacement plans cover at most 500 files and 256 MiB, and 10 undo snapshots are kept. Scope testing: 5000 scopes and 2000 matches per run, 2 s. Hex view: 4 KiB. Loading a file: the first 64 KiB. Pattern comparison: 8 patterns, 4 s.

      Search and the regular expression builder
      Complete source: docs/features/search-and-regex.md
      Search and the regular expression builder
      

      Every search and filter field in the application, including lists, tables, logs, source viewers, pickers, menus, settings, the command palette and tab search, uses the same search field. Each field has its own regular expression builder beside it.
      

      Plain text first
      

      A search field matches the text exactly as you type it, ignoring case. Characters such as ., * or ( have no special meaning in this mode.
      

      Regular expressions are opt-in. Turn on the .* toggle at the end of the field, or insert something from the builder. Each field remembers its mode, flags and sample text only while it exists. Nothing is written to disk unless you choose Save to my patterns or Remember this experiment, or you apply a replacement in files (see below).
      

      Opening the builder
      

      • Press Alt+R while the field, its .* toggle or its builder button has focus.
      

      • Select the builder button (tune icon) next to .*, or right-click .*.
      

      The builder opens as a panel attached to the field. It opens below the field, or above it when there is no room below, and its content scrolls when the window is small (960 x 720 and up). Tab moves through its controls and stays inside the panel. Esc or Done closes it and returns focus to the field. Clicking elsewhere also closes it, and focus stays where you clicked.
      

      What the builder offers
      

      • Pattern: the raw pattern, synchronized both ways with the search field. If the pattern is invalid, the builder shows the framework's message, and the panel underlines the character where the error was found.
      

      • Flags: toggle chips for IgnoreCase, Multiline, Singleline, IgnorePatternWhitespace, ExplicitCapture, CultureInvariant, RightToLeft and NonBacktracking. IgnoreCase also applies to plain-text mode. RightToLeft runs on the backtracking engine. NonBacktracking requires the linear-time engine and reports patterns that need backtracking instead of falling back.
      

      • Guided insertion at the caret:
      

        - Text: plain text with automatic escaping, and a list of alternatives inserted as (?:a|b).
      

        - Classes: \d \w \s and their negations, ., Unicode categories such as \p{L} (with a negate option), and a custom or negated [set] editor that escapes ] \ ^ - for you.
      

        - Anchors: ^ $ \b \B \A \z.
      

        - Groups: capturing, named (?<name>...), non-capturing, lookahead and lookbehind (positive and negative), atomic, alternation |, and backreferences \1 or \k<name>. Group buttons wrap the selected part of the pattern.
      

        - Repeat: ? * +, their lazy forms, and {n}, {n,}, {n,m} with an optional lazy suffix.
      

      • Blocks: build a pattern from plain-language lines such as start of line, literal v, capture major: digits 1 to 3 times, one of cat|dog, optional literal s, end of line. Literal text is escaped. Use this pattern or Insert at caret applies the result.
      

      • More: characters by code point (\xHH, \uHHHH, surrogate pairs), \n \r \t \f \v \e \a \0, \Z, \G, class subtraction [a-z-[aeiou]], conditionals (?(1)a|b), balancing groups (?<push-pop>...), inline options (?i-s:...), comments, and the atomic stand-in (?>item+) for possessive quantifiers. Constructs .NET does not have are listed with the reason.
      

      • Library: ready-made patterns for an image reference, an image tag, a sha256 digest, a semantic version, IPv4 and IPv6 addresses, a port number, a container or image ID, an ISO 8601 date, an email address, a URL, a Windows path, an environment variable NAME=value line and a log level. Each has a worked example. Use replaces the pattern; Insert adds the pattern at the caret.
      

      • My patterns: Save to my patterns stores the name, pattern and flags in regex-patterns.json in the application data folder (%LOCALAPPDATA%\DingDingProjects\MaterialDockerImage). The file holds at most 200 entries, and you can remove any of them. The sample text is never saved with a pattern. The replacement and the test cases are saved with it only when Also save the replacement and the test cases is ticked (it is ticked by default), and loading the pattern restores them. Import… adds patterns from a library file (existing names are kept; patterns that do not compile are skipped and reported) and Export… saves all of them to a file you choose. A filter box searches names and patterns. Recent in this field lists valid patterns used in that field during this session. The list is kept in memory only.
      

      • Explanation: a tree that describes each token of the pattern in plain English. It covers literals, escapes, classes, Unicode categories, anchors, groups, lookarounds, alternation, quantifiers, backreferences, inline options and comments. Selecting a row highlights that token in the pattern, and moving the caret in the pattern selects the deepest row at that position. Detail (Overview, Standard, Full) limits how many levels are shown and exported. Copy explanation and Save explanation… export the tree as indented text, Markdown or JSON at that detail (up to 2000 tokens).
      

      • Test: paste up to 64 KiB of sample text. The builder highlights matches, shows zero-width matches as thin markers, gives the match count, and lists capture groups in a table (match, group number, name, value, position). Previous match and Next match (Shift+F3 and F3) step through the matches with wrap-around, mark the current one in a second colour and select it in the sample box.
      

      • Replace preview: a replacement using $1, ${name}, $0 or $&, ` $ `, $', $+, $_ and $$. The preview shows the sample after replacement and warns about references to groups that do not exist (.NET inserts those as plain text). A palette inserts each reference at the caret, **Replacement explained** describes every piece in plain words, and **Insert characters** turns typed escapes (\n, \t, \xHH, \uHHHH, \u{...}) into the characters themselves, because .NET replacement text has no escapes of its own. **Insert as literal text** doubles every $`. Nothing in the application is changed.
      

      • Split preview: shows how the sample is cut at each match (up to 2000 pieces). With capture groups, the captured text is returned between the pieces, as .NET does.
      

      • Test cases: lines starting with + must match and lines starting with - must not match. The builder reports how many hold. Kept in memory for the field only.
      

      • Diagnostics and timing: a static check flags nested unbounded repeats, repeated or overlapping alternatives under a repeat and adjacent .*.*. Run timing probe measures wall-clock time on growing inputs with the backtracking engine (250 ms per probe, 3 s total) and warns about catastrophic backtracking. .NET exposes no step count or match trace, so none is shown.
      

      • Convert and copy as: C# (verbatim string, regular string, code for finding, testing, replacing or splitting), PowerShell, a JSON string, command lines for grep -E, grep -P, ripgrep and Select-String, and code for JavaScript, Python, Java, Go and PHP. The grep -E conversion works construct by construct and refuses what grep cannot express (lazy quantifiers, lookarounds, atomic groups, conditionals, inline options, Unicode escapes and some flags); rewrites that change meaning are labelled. The other targets use the flavor table: a construct the target does not support stops the conversion and names it, and a construct it reads differently is listed and marks the result as not identical in meaning. The command lines use the folder and file patterns from Search in files when they are filled in; their quoting is for a POSIX shell (PowerShell for Select-String). ripgrep gets -P when only PCRE2 can read the pattern.
      

      • Parameters: write {{name}} or {{name:default}} in a pattern. The pattern still compiles as written, so a saved pattern with placeholders stays valid. The Parameters tab lists the placeholders, takes a value for each and fills the pattern in a single pass: values are escaped as literal text unless Insert values as pattern fragments is ticked, a value that itself looks like a placeholder is never expanded, and a filled pattern that does not compile is refused. Turn selection into parameter writes the placeholder for you. Using a saved pattern that has placeholders tells you how many to fill.
      

      • History: Remember this experiment stores the pattern, flags, sample (up to 16 KiB), replacement and test cases in regex-experiments.json in the application data folder (50 experiments, 1 MiB at most; the oldest go first). Nothing is stored until you press the button. Load restores a whole experiment, Forget removes one and Forget all clears the file. The sample is part of what is stored, so do not remember text you would not keep on disk.
      

      • Flavor comparison: lists, for the constructs this pattern uses, which of seven engines (.NET, PCRE2, JavaScript, Python re, Go RE2, Rust regex as used by ripgrep, and grep -E) read them the same way, read them differently or do not support them. The table is written by hand (37 constructs) and each probe was run against the real engines while it was written; nothing is executed in another engine when you use it. It can be copied as text.
      

      • Search in files: searches the files of a folder with the pattern (flags and plain-text mode included). Folder, file patterns (*.log;*.txt;!*.min.js, ?, **; a slash means a path from the folder), subfolders and the largest file are set in the panel and remembered while the field exists. .git and node_modules are skipped, links and junctions are never followed, binary files (a NUL byte in the first 8 KiB) are skipped, and UTF-8 and UTF-16 with a byte order mark are read. Results list file, line, column and the line text; the limits are 2 MiB per file (adjustable up to 16 MiB), 5000 files, 1000 results, 200 matches per file, 128 MiB in total and 15 seconds, and each limit that stops a search is reported. A whole drive is refused.
      

        - Preview replacement is a dry run: it writes nothing and needs no backup. It lists, per file, the number of replacements and the first changes with line and column. Files that are not valid in their encoding, read-only files and files over a limit are skipped with the reason.
      

        - Apply… is available only after a preview of the current pattern, replacement, folder and file patterns, and asks for confirmation. It re-reads each file and skips any that changed since the preview (SHA-256 comparison), writes a byte-exact undo snapshot of every file it will change into regex-undo in the application data folder, then writes each file with its byte order mark and line endings preserved. If a write fails, the files already written are restored. A plan covers at most 500 files and 256 MiB, and the 10 newest snapshots are kept. The event is recorded in Local History (the summary, not the file contents).
      

        - Undo on a snapshot restores the original bytes of each file that still has the content the replacement wrote; a file edited afterwards is left alone and reported.
      

      • Convert POSIX classes (More tab) rewrites [[:alpha:]] and the other POSIX classes as .NET sets; the diagnostics warn when a pattern contains one, because .NET reads it as a different set.
      

      • Copy pattern, Copy as C# string (a verbatim @"..." literal), and Export JSON (pattern, flags, engine, dialect, sample and replacement).

      Engine and limits
      

      Matching uses .NET regular expressions (System.Text.RegularExpressions). The builder states which engine runs the pattern:
      

      • Non-backtracking engine (RegexOptions.NonBacktracking), used whenever the pattern allows it. Matching time grows linearly with the text, so a pattern such as (a+)+$ cannot hang the application.
      

      • Backtracking engine, used only for constructs the non-backtracking engine does not support: lookarounds, backreferences, atomic groups and conditionals. Each match is limited to 250 ms.
      

      Limits:
      

      • Patterns can be up to 4096 characters.
      

      • Sample text can be up to 64 KiB (UTF-8); longer text is cut, and the builder says so.
      

      • At most 2000 matches are highlighted and 2000 split pieces are shown.
      

      • A test stops after 2 seconds in total.
      

      • Replace output is cut at 256 KiB.
      

      Tests and replace previews run off the interface thread and are cancelled when you keep typing. An invalid pattern never raises an error dialog. The field shows a clear message, filtering shows nothing until the pattern is fixed, and bulk actions refuse to run. If a backtracking pattern times out while filtering a list, the field stops matching for that query and asks you to simplify it.
      

      Escaping rules
      

      To match one of \ * + ? | { [ ( ) ^ $ . # literally in a regular expression, put a backslash before it. With IgnorePatternWhitespace, a space must also be escaped. Inside [ ], escape \ ] [ ^ -. Insert escaped text does this for you. Plain-text mode needs no escaping.

      Settings safety: locks, schedules, attention modes, sounds and collapsible filters
      Complete source: docs/features/settings-safety.md
      Settings safety: locks, schedules, attention modes, sounds and collapsible filters
      

      This guide covers five related controls in Settings and the shell. Every rule below is a framework-free class in src/MaterialDockerImage/UI/SettingsSafety.*.cs with focused checks in tests/UiState/Program.cs. The window code only reads their decisions. None of this has been driven in the built window yet; see the verification section.
      

      Element locks
      

      Every settings row that holds a value has a lock button beside its title, and every row and every interactive element on a page has Lock this control... on its right-click menu: buttons, switches, check boxes, options, drop-downs, text fields and sliders. Locking an element shares one helper (Shell/LockUi.cs) between settings rows, page buttons and every other element. Major page action buttons (the filled and danger buttons) keep their ids btn.<page>.<label> in lower case, at most 40 characters, so two buttons with the same label on the same page share a lock.
      

      Locks on any element
      

      LockUi.AttachPage walks each page when it is shown and attaches the lock menu to every supported element that does not already have one. The id comes from ElementIdentity.Derive (UI/SettingsSafety.LockManager.cs): el.<page>.<kind-name>-<hash>, at most 36 characters and always a valid lock id.
      

      • An element with an AutomationProperties.AutomationId keeps the same lock when it moves or is renamed. No page sets one today, so in practice the next rule applies.
      

      • Otherwise the id is built from the page, the element kind, the English name (Loc.Original turns a translated accessible name back into English, so switching language does not change the id) and the position among identical elements on that page, so two identical OK buttons get two locks.
      

      • A name that is a sentence with numbers in it is not reversed to English, and an element whose accessible name changes for another reason gets a new id. Elements built after the page is shown are picked up the next time it is shown. Settings rows keep their own lock and are skipped.
      

      • Tabs, tab groups and individual appearance values are lockable too, and clicking a locked control opens its unlock prompt: see the section on tab, tab group and appearance locks below.
      

      • A locked row or button is disabled, and a page that re-enables it (for example after an async action) is overruled. The right-click menu stays available on a locked element and offers Unlock this control.... The settings lock button also stays enabled as the unlock target. A disabled button cannot be clicked or focused, so unlocking a page button needs its context menu.
      

      • Locks are stored in settings.json as LockedSettings (identifiers, at most 200) and every lock or unlock is recorded in local history ("Locked setting: ..."). The history never holds a credential.
      

      • Import and Reset all keep locked rows at their current values (ElementLocks.Preserve). Reset leaves the locks themselves in place. A lock on a button has no settings value to preserve.
      

      • The command palette controls (theme, language, sounds, motion, contrast, the attention modes and School mode) and the accessibility menu are disabled while their row is locked, so a lock cannot be walked around.
      

      Lock policies
      

      The first time a control is locked, a wizard asks what unlocking should require. The choice is kept per lock and reused on the next lock; Change lock policy... reopens the wizard on an unlocked control and Remove lock policy... deletes the credential.
      

      | Policy | Unlock asks for | Stored as |
      

      | --- | --- | --- |
      

      | None | A confirmation that repeats the disclosure below. | Nothing. |
      

      | PIN | 4 to 12 digits. | A PBKDF2-SHA256 hash (150,000 iterations) with a random per-hash salt, mixed with a random per-install salt kept in the lock file. The PIN is never stored, logged or exported. |
      

      | Password | 8 to 128 characters, no control characters. | A PBKDF2-SHA256 hash with the same parameters as the PIN. The password is never stored, logged or exported. |
      

      | Authenticator app | A 6-digit RFC 6238 code (SHA-1, 30 seconds, one step of clock skew either side). A code that was accepted cannot be used again. | The 20-byte secret, generated with RandomNumberGenerator, protected with Windows DPAPI for the current user (entropy: the install salt). |
      

      | PIN plus password, password plus authenticator, PIN plus authenticator, password plus PIN plus authenticator | Every factor of the policy, always asked in the order PIN, password, authenticator code. | Each factor as above, in the same lock record. |
      

      A combined policy is one bounded attempt (LockStore.Begin, UnlockAttempt). The dialog shows Step n of m. A factor that is right is remembered only inside that attempt, so closing the prompt starts again at the first factor. A wrong answer at any step counts once against the lock's single attempt budget and sends the attempt back to the first factor; the authenticator step is spent only when every factor is right, so a code cannot be replayed. One value cannot answer a combined policy. A factor that cannot be checked (the authenticator secret cannot be read) is reported as unavailable and never skipped.
      

      The stored policy numbers are None 0, PIN 1, Authenticator 2, Password 3, PIN plus password 4, Password plus authenticator 5, PIN plus authenticator 6, Password plus PIN plus authenticator 7. Existing numbers never change, a lock file written before durations loads, and an unknown number is dropped.
      

      Credentials live in locks.json in the data folder, apart from settings.json, exports and history. An authenticator lock needs DPAPI; where it is unavailable the wizard says so and refuses the policy. In capture mode the store is held in memory only.
      

      Pairing an authenticator shows the secret only after Show secret and QR code: a QR code of the otpauth://totp/ link, the grouped Base32 secret, copy buttons and the algorithm, digits and period. The lock arms only after one current code is typed back.
      

      Unlock durations
      

      The wizard asks how long an unlock lasts (UnlockDuration, stored with the lock):
      

      | Choice | The lock closes again |
      

      | --- | --- |
      

      | This action only | After the protected action: a button click, a drop-down or slider change, a text field that lost focus with new text, or, for a settings row, the first save that changes its values. |
      

      | 5 minutes, 1 hour | When the time is up. The expiry is saved in locks.json, checked every 15 seconds while the app runs, and honoured across a restart. |
      

      | Until the app closes | At the next launch, always. This is the default for a new lock. |
      

      Locks written before durations existed read as "until I lock it again" and are never closed by themselves. Locking again by hand ends the grant. LockLifecycle (UI/SettingsSafety.LockManager.cs) holds these rules; the launch pass and the timer call LockLifecycle.Reconcile. The record keeps only a flag and a time, never a credential.
      

      Locks manager
      

      Settings has a Locks section: one table of every lock the app knows, whatever it guards, with the lock id, what it is, its policy, how long an unlock lasts and whether it is locked or unlocked until a time. It has the shared search with its regex builder, the filters Locked only and Has a credential, export (the shared table export) and row actions Unlock this control..., Lock again, Change lock policy..., Remove lock and Support Tickets.... Remove selected locks removes many at once. A lock that is locked is never removed: it has to be unlocked first, and a bulk removal reports the locked ones it skipped. Removal deletes the lock, its credentials, its recovery codes and its label. The command palette has Locks manager. Labels for locks that are not settings rows are kept in settings.json (LockLabels, descriptions only, never a credential). An export contains only descriptions, never a hash or a secret.
      

      Unlock ladder
      

      Unlocking climbs these rungs (LockStore.Stage, LockStore.Attempt, LockStore.UseRecoveryCode):
      

      1. Confirm. A lock with no policy only asks for a confirmation.
      

      2. Credential. The PIN, password or authenticator code, one step at a time for a combined policy. The first two wrong answers cost nothing and the dialog says how many free tries remain.
      

      3. Wait. From the third consecutive wrong answer the wait is 30 seconds, then 60, 120 and so on, doubling to a cap of one hour. The dialog shows a live countdown and the clock time the wait ends. The failure count and the wait are saved, so a restart does not clear them. While waiting, an answer is refused without being checked and without counting. Waiting alone never unlocks anything: the credential is still needed afterwards.
      

      4. Recovery code. Eight single-use codes (XXXXX-XXXXX) are made when a PIN or authenticator policy is saved, shown once with Copy all and Save to file, and stored only as hashes. A code works at any time, including during a wait, clears the failure count and the wait, and is spent. Typing ignores case, spaces, hyphens and the look-alike letters I, L and O.
      

      Beside every prompt the dialog names the data folder and says that deleting locks.json (or the whole folder) clears every lock. That is the last resort when the PIN, the authenticator and every recovery code are gone.
      

      Tab, tab group and appearance locks, the disabled-click prompt, locked labels and the keypad
      

      These are framework-free rules in UI/SettingsSafety.TabLocks.cs, UI/SettingsSafety.AppearanceLocks.cs and UI/SettingsSafety.PinKeypad.cs, checked in tests/UiState/LockExtraChecks.cs. The window code only asks them.
      

      Tab locks. Every tab has its own lock, found by its destination (tab.<destination>). A locked tab keeps its readable name and shows a lock icon. It refuses switching to it, closing it, moving it and pinning or unpinning it. Selecting a locked tab does not open it: the strip goes back to the tab that is really shown and the unlock prompt opens; once the person gets through, the tab opens. The tab's right-click menu has Lock this tab... (with Change lock policy...) and Lock this tab group.... The rail destinations have Lock this destination... (the same per-destination lock) and Lock the navigation rail.... Navigation is checked in one place (MainWindow.Navigate and OpenTab), so a shortcut, the palette and a rail click cannot walk around a locked destination.
      

      Tab group locks. The app has no user-made tab groups yet, so the groups are its three regions: Pinned tabs (including the workspace tab), Open tabs and the Navigation rail. A group lock is a separate lock with its own policy and credentials. It refuses closing, moving and pinning for every tab in the group; for the rail it refuses switching destination by clicking the rail. It never relocks the members: a locked tab in a locked group answers to its own lock first, and unlocking one leaves the other standing. The Locks section has a button for each group.
      

      Bulk close. Locked tabs, and tabs in a locked group, are excluded from Close other tabs and Close tabs containing / not containing text exactly as pinned tabs are. The preview says "locked" beside them. Include locked tabs puts them in the preview, and even then each locked tab asks for its unlock before it closes.
      

      Appearance value locks. Every value of the appearance editor can be locked: theme, seed colour, colour roles (all, or each colour role on its own), corner radius, density, interface and code fonts, font size, heading weight, rail icon style, elevation, surface tint, rainbow accent, motion level and speed. A check compares the list with the members of AppearanceState, so a new value cannot be left out. A saved preset can be locked (it cannot be replaced, renamed or deleted). For a customized element, every property (background, text colour, corner radius, font size, weight, padding, visibility) has its own lock from the switch's right-click menu, the whole element has one lock, and Lock every property... gives each property its own wizard, policy and credentials. A lock holds the value whoever asks: the editor, a preset, a paste, undo and redo, an import, a reset, or the element editor all keep a locked value as it was (AppearanceLocks.GuardState, Guard, GuardRoles), and say so in a notification. A locked element property is disabled in the editor.
      

      Clicking a locked control. A locked control is still disabled. A left click that lands on it (hit-tested at the pointer, because a disabled element does not get the event) is swallowed, the protected action does not run, and that control's own unlock prompt opens, at most one prompt per lock (UnlockPromptGate). It is installed on the main window and on the element editor, and covers settings rows, page controls and the element editor's switches. The prompt is the shared unlock dialog, which is an overlay in the window, not a prompt anchored beside the control. A disabled control cannot take keyboard focus, so the keyboard route for it is the lock button of a settings row, the Locks section and the control's context menu; tabs are focusable and prompt when activated.
      

      Locked labels in searches and the palette. The command palette lists a guarded command with a Locked chip and the word "locked" in its accessible name; choosing it asks for the unlock and does not run the command. Go-to commands answer to the destination's tab lock and the settings commands (theme, motion, contrast, language, sounds, the attention modes, School mode) to their settings row. Search open tabs and the New tab catalog label locked tabs and match the word "Locked". Hide locked items in searches (Locks section, off by default) leaves them out, and each list then says how many it hid.
      

      Keypad PIN entry. The unlock prompt shows a keypad under the PIN field for a PIN step: 1-9, then Clear, 0 and Backspace, large buttons with their own accessible names. It fills the same field the keyboard fills, and submitting goes through the same single validator and attempt budget as typing, so a wrong PIN on the pad costs the same attempt and a wait applies to it equally. A screen reader hears how many digits are entered, never which. The pad has no paste. Shuffle the keys (off by default, kept in settings) randomizes the digit positions.
      

      What these do not cover: the PIN wizard that sets a PIN has no keypad (only the unlock prompt does); there are no user-made tab groups, no tab-group search and no all-windows master tab search, because the app has none of those surfaces; commands that pages register themselves are not mapped to locks; colour role names in the "kept as they were" notification are not translated individually.
      

      Games that shorten a wait
      

      While a wait is running, the Wait rung offers Play to shorten the wait. The games run in this order, and a win ends the wait early. (UI/UnlockLadderGames.cs makes and grades every question; Shell/LadderGameDialogs.cs only shows them and collects answers.)
      

      | Rung | What it asks | Clears the wait | Otherwise |
      

      | --- | --- | --- | --- |
      

      | Dish | One dim sum dish, four choices. With a picture from the public catalogue it asks which dish it is; with no picture (offline, or the picture could not be fetched) it shows the Cantonese name and asks for the English one. The picture alt text never names the dish. | The right choice | Up to five wrong choices, then the sums. Wrong choices are counted per lockout, so closing the dialog does not reset them |
      

      | Sums | Ten sums (a + b, a - b with a non-negative answer, a x b with single digits). Every one must be right | Ten right | One wrong, missing or wrong-kind answer drops to whack-a-mole |
      

      | Whack-a-mole | A 3 by 3 board, 14 moles one at a time for one second each, 20 second round. Click a mole or press keys 1 to 9. At least 8 hits | 8 or more counted hits | A lost round ends the ladder |
      

      | Clock | The plain wait | | The ladder is not offered again for that lockout |
      

      What keeps it from becoming a second, weaker password:
      

      • A win clears the wait only. It signs nobody in, mints no session and sets no cookie; the prompt returns to the credential rung and the PIN or code is still required. LockStore.ClearWaitByLadder changes nothing except the running wait.
      

      • It never refunds the attempt budget and never slows the escalation: the failure count is untouched, so the next wrong answer still earns the longer wait.
      

      • A rolling budget of three wins per hour (LadderLedger, kept in ladder.json beside locks.json) caps it. After that the Wait rung says the clock is the way through until an hour has passed. Deleting ladder.json only refills the budget; it does not touch any lock.
      

      • Every question carries a random single-use nonce that is taken out of the table before anything is graded, so a wrong answer cannot be retried against the same question, a right one cannot be replayed, an answer for another lock or of the wrong kind is refused, and challenges expire (5 minutes for a dish, 10 for sums, the round plus a minute for moles). The correct answers are not on the challenge objects the views receive. This app grades in the same process as the views, so this is separation of duties inside one program, not a security boundary, and the disclosure above still applies.
      

      • A mole round answered before its 20 seconds could have elapsed is refused. A hit counts only for a mole that was in that cell at that moment, inside the round, and each mole counts once.
      

      • Under School mode the ladder starts at the sums: the dish rung is absent, and no copy names it.
      

      The dialogs use the real keyboard path (number keys for choices and cells, Enter on the last sum), a numeric seconds-left readout beside the round (never colour-only), a live region for the score, no animation, and large cells.
      

      Not built: the access-control style keypad for PIN entry; locks on tabs, groups and individual appearance values; locked items labelled in the command palette and tab searches. Grading runs in the same process as the views. The three games have been checked as rules only; none has been driven in the built window.

      Dim sum surprise
      

      At startup there is a 10 percent chance, from one fresh random draw per launch, of a small toast with a dim sum dish: its name in the active language mode and, when it can be fetched, its picture. It cannot be switched off. It stays polite by staying out of the way: it never appears during first-run setup, with a dialog open, while an update is ready, while an operation runs, in quiet hours, under School mode or in a capture run, and never twice in a launch. It does not take focus, announces itself through a polite live region, fades in only when motion is on, and removes itself after nine seconds (longer while hovered or focused).

      • The catalogue index is read from its raw URL and trimmed into a small cache (dimsum\catalog-cache.json in the data folder) that records the source URL and revision (ETag); it is refreshed after seven days with a conditional request.
      

      • A picture is downloaded once from the published catalog-v1* release assets (tried in order), must start with the PNG signature and be under 12 MB, and is kept in a cache of at most 24 pictures. No photo is stored in this project, and no photo is attached to its releases.

      • The only requests are two public reads of that catalogue. No personal data is sent and nothing is tracked.

      Support Tickets
      

      The recovery route for a locked-out person is dressed as a support desk. It is reached from the unlock prompt (Forgotten your password?), from the footer of the lock wizard, the ladder and the Locks manager (Support Tickets...), from the Tools page (Support Tickets) and from the command palette. The code is Shell/SupportDeskUi.cs and UI/SettingsSafety.SupportTickets.cs.
      

      • Filing. A category (forgot my PIN, forgot my password, lost my authenticator, lost my recovery codes, something else), a severity and a description of up to 1,000 characters. The ticket number is generated locally (TKT-yyyyMMdd-0001, counting up within a day). A blank description is refused. The list holds at most 200 tickets.
      

      • Severity. It is recorded and then treated exactly like every other severity, and the screen says so.
      

      • Status. New, acknowledged, investigating, resolved. It advances on request (Advance status), by itself every 20 seconds while the screen is open, or straight to resolved (Resolve, which still records every reply). Each step adds a canned reply. The factual sentence is always shown; a playful lead-in is added by the funny level.
      

      • Resolution. The resolution opens the application-data folder in the platform's file manager (PageParts.OpenFolder, which reports a failure to launch) and shows the exact path with a copy button. The path shown and the folder opened are the same value. The app never deletes anything: SupportDesk.Resolve returns only the folder to open, and a check asserts that neither source file contains a delete call.
      

      • The disclosure. One plain line, outside the comedy and identical at every funny level and in every language mode, states: nothing is sent anywhere, a ticket exists only on this computer, no network request is made, no data is collected, and nobody is reading it. A check pins its exact wording and asserts that the source files contain no network call.
      

      • Storage. Tickets live in tickets.json in the data folder, so deleting the data folder clears them with the locks they point at. The list uses the shared table: search with its regex builder, export, row actions and bulk Advance, Resolve and Remove.
      

      No real person, company, case system or response time is named or implied.
      

      Authenticator tool

      My accounts (general authenticator)
      

      Keeps the time-based one-time codes for any account you register.
      

      • Adding: paste an otpauth://totp/ link (issuer, algorithm SHA1, SHA256 or SHA512, 6 to 8 digits and the period are taken from the link, never replaced by defaults) or enter the issuer, account, Base32 secret, algorithm, digits and period by hand. Spaces, hyphens and lower case in a secret are tolerated; counter-based (HOTP) links, unsupported algorithms, repeated parameters and links over 2,048 characters are refused with a plain reason.
      

      • Codes: each account shows its current code grouped for reading (123 456), the seconds left as a number and a bar (never colour only; the number turns to the warning colour in the last five seconds) and the next code. Copy puts the current code on the clipboard.
      

      • Managing: search (with its own regular expression builder), rename, move up or down and delete with confirmation. At most 200 accounts; an exact duplicate is refused.
      

      • Storage: one file, authenticator.bin, protected for the current Windows account with DPAPI. The whole document is encrypted, so issuers and names are protected as well as secrets. A file this account cannot open, or that is damaged, is reported and never overwritten. Nothing is written to settings.json, local history, notifications, logs or exports.
      

      • Backup: Export encrypted backup… writes AES-256-GCM with a key derived from a passphrase (at least 8 characters) by PBKDF2-SHA256 (600,000 iterations), a random salt and nonce. Import encrypted backup… validates everything before adding anything, skips accounts already present and refuses wrong passphrases, changed files, unsafe key settings and oversize files.
      

      • Capture mode shows three labelled sample accounts with example data and disables adding and backups, so a HuiShot never shows a real secret or code.
      

      Standards: codes come from RFC 4226 and RFC 6238 and are checked against all 18 published RFC 6238 vectors through the account model.
      

      Not built: registering from a QR image file, the clipboard or a camera, grouping, a warning when the system clock is far off (this needs a trusted time source), a secrets export behind super confirmation, and any driving of the section in the built window.
      

      App locks
      

      Tools has an Authenticator section for the app's own locks. It pairs an authenticator app with a lock, checks a code for a lock without using it up or counting it as an unlock attempt, lists the locks that have a policy (with their recovery codes left and Remove policy) and runs Run RFC 6238 self-test, which computes the 18 published RFC 6238 vectors (SHA-1, SHA-256, SHA-512, 8 digits) with the build's own code. The command palette has Authenticator for locks. A lock registered in an authenticator on the same computer is mostly for fun, since the key sits beside the lock it opens.
      

      The QR encoder (UI/SettingsSafety.Qr.cs) is dependency free and draws nothing itself: byte mode, level L, versions 1 to 10 (271 bytes). Text beyond that is refused rather than truncated, and an otpauth link for a lock fits easily.
      

      Scheduled settings
      

      Settings, Schedules. A rule lends one setting for a time window and, optionally, a date range. Seven settings can be scheduled; each is decided on its own.
      

      | Setting | Allowed values | What it changes while lent |
      

      | --- | --- | --- |
      

      | Language | English, Cantonese, Bilingual | The interface language |
      

      | Theme | Dark, Light, System | The colour scheme |
      

      | Density | Compact, Comfortable, Spacious | Control height and padding |
      

      | Accent colour | #RRGGBB | The seed colour that all colour roles derive from |
      

      | Font size | Whole number 12 to 22 | The base font size |
      

      | Motion | Off, Reduced, Standard, Expressive | The motion level |
      

      | Display name | 1 to 80 characters, no control characters | The title bar and window title |
      

      | Field | Meaning |
      

      | --- | --- |
      

      | Source | Local (the rule's own value), File, HTTPS (the value for the rule's setting comes from that source) or Home Assistant (on and off map to two values) |
      

      | Days | Every day, or chosen weekdays |
      

      | From, until | Local clock times, HH:mm. The end is not included. |
      

      | First date, last date | Optional local calendar dates, yyyy-MM-dd, both days included. Empty means no bound on that side. |
      

      | Priority | -5 to 5 in the editor (stored range -100 to 100) |
      

      Semantics, all covered by checks:
      

      • Times are in this computer's time zone and follow daylight saving changes.
      

      • A window is from the start up to, but not including, the end.
      

      • Equal start and end mean the whole day (still limited to the selected weekdays and dates).
      

      • A start later than the end crosses midnight. The part before midnight uses that day, the part after midnight belongs to the window that started the day before. The weekday and the date range are both judged on the day the window started, so a window that starts on the last date finishes after midnight.
      

      • Weekdays and dates must both match. An unreadable date makes the rule inactive and is refused by the editor.
      

      • A rule with an unparseable time, no weekday selected or a disabled switch is never active.
      

      • Higher priority wins; equal priorities: the later rule in the list wins. Each setting is decided independently of the others, so a priority on one setting never blocks another.
      

      • At most 50 rules; duplicate or missing identifiers are repaired on load.
      

      A schedule only lends its value. UserSettings.ApplyScheduled keeps the person's own choice as the base for every lent setting and ToJson always writes the bases, so the saved file never contains a borrowed value (a font size of 14.5 comes back as 14.5). When the window ends the base is put back. If the person changes a lent setting by hand, that choice becomes the new base instead of being overwritten.
      

      The runtime (Services/ScheduleRuntime.cs) evaluates every 20 seconds, when rules change, when the source file changes and whenever a network source answers, and shows one non-blocking notice when the applied values change.
      

      Value sources
      

      Rules whose source is File, HTTPS or Home Assistant take their value from outside. A rule whose source cannot supply a value stays inactive, and your own setting stays in effect.
      

      Local file. An optional JSON file chosen in Settings, Schedules, watched with a debounce and only ever read from disk:
      

      { "version": 1, "language": "Cantonese", "theme": "Light", "density": "Compact", "accent": "#AA3366", "fontSize": 16, "motion": "Reduced", "displayName": "Night desk" }
      

      Every field except version is optional. No other field is accepted, a field may appear only once, the nesting depth is limited, the version must be 1 and the file must be under 4 KiB. Anything wrong refuses the whole file so nothing is applied from a half-valid document.
      

      HTTPS. One address, entered by the person, that returns the same document (up to 64 KiB).
      

      • Only https:// addresses are accepted. A user name or password in the address, a fragment, whitespace, and query parameter names that look like secrets (token, key, password, auth, signature and similar) are refused, so nothing secret is ever saved in plain text in settings.json.
      

      • The app sends only a GET, with no cookies and no credentials, waits 10 seconds at most, reads 64 KiB at most and does not follow a redirect to plain http.
      

      • Checking is automatic no more often than every 5 minutes (choices from 5 minutes to 24 hours), and only while an enabled rule uses the source. A "Check now" button asks at once.
      

      • If the server cannot be reached, times out, answers an error, answers something too large or answers a document that fails validation, the last good answer stays in use, no setting changes, and the state line says so, for example "Offline: The server could not be reached. The last good answer from 25 minutes ago stays in use and nothing was changed." With no earlier good answer, nothing from the source is applied. Errors are fixed wording; the address and server text are never copied into messages or logs.
      

      Home Assistant. A base address, an entity id such as input_boolean.night_mode, and a long-lived access token.
      

      • The token is encrypted with Windows data protection (DPAPI, current user) and stored in its own file ha-token.bin in the data folder. It is never written to settings.json, exported, logged or shown again; a check proves UserSettings has no property that could hold a secret. Without a token the state line says "No token is stored" and nothing is requested. A token that cannot be decrypted (for example a copied file) is reported as unreadable.
      

      • Plain http:// is accepted only for loopback, private-network and link-local addresses and for local names (localhost, a name without a dot, .local, .lan, .home.arpa). Every other host must use https://, so the token is never sent in clear text over the internet.
      

      • The app sends only GET /api/states/<entity> with the bearer token, waits 10 seconds at most and reads 64 KiB at most. The answer must be for the same entity.
      

      • The state on applies the rule's value; off applies the optional value for off (nothing if it is empty). Every other state (unavailable, unknown, a number) applies nothing.
      

      • Checking runs every 1 minute to 24 hours as chosen (default 5 minutes) while an enabled rule uses the source. Failure behaves exactly like the HTTPS source: the last good state stays and nothing changes.
      

      Every rule add, change, enable, disable and delete, every change to a source and every token store or removal (the token itself is never recorded) is saved with a local history record.
      

      Attention modes
      

      All five are independent switches in Settings, Focus modes, and in the command palette. AdhdRules.Resolve is the single decision the window reads.
      

      | Mode | What it changes |
      

      | --- | --- |
      

      | Focus | Hides the version line and the accessibility button, narrows the rail and hides its labels, and shows an Exit focus button in the title bar. Nothing is removed that cannot be brought back in one step. |
      

      | Low stimulation | Turns off action sounds and animation, and hides the Momentum chip. It adds to, and never overrides, Reduced motion and the Windows animation setting. |
      

      | Time awareness | Shows a clock in the title bar. |
      

      | One thing at a time | Opening another destination reuses the current tab. |
      

      | Momentum | Shows a chip with the number of operations finished in a row this session. A failure or a cancel resets it. The streak is never saved. |
      

      Momentum is fed by AppHost.Execute, so it counts real Docker operations only.
      

      Action sound effects
      

      One playback path, Services/ActionSounds.cs. A cue plays only when the Action sounds switch is on, Low stimulation is off, the window is not producing captures, the volume is above zero and it is not inside the quiet hours (SoundCueRules.MayPlay). Playback runs on a background task and any playback problem is swallowed, so a missing audio device never changes the result of an action.
      

      | Cue | Triggered by | Windows sound |
      

      | --- | --- | --- |
      

      | Success | An operation or build finished successfully | Asterisk |
      

      | Failure | An operation or build failed | Hand |
      

      | Warning | A warning notification, or a canceled operation | Exclamation |
      

      | Removal | A remove, prune, kill or delete operation finished successfully | Question |
      

      | Copy | Text was copied to the clipboard (after the clipboard accepted it) | Beep |
      

      | Drop | A dropped wording file was applied | tada.wav, or Asterisk if missing |
      

      | DropRefused | A dropped file was refused | Beep |
      

      The mapping is SoundCueRules.Mapping; a check requires every cue to have a row. The same table appears in Settings, Sounds and narration. No audio file ships with the app.
      

      Volume
      

      Settings, Sounds and narration, Action sound volume: 0 to 100 percent, saved as SoundVolume (default 100) and applied to the very next sound, with a "Play a test sound" button.
      

      • At 100 percent the Windows system sound plays at its own level, exactly as before.
      

      • Below 100 percent the app finds the WAV file Windows plays for the cue (from the person's own sound scheme in the registry, falling back to the stock file in the Windows media folder), scales its sample amplitude in memory (WavScaler, 8, 16 and 24 bit PCM) and plays that copy through SoundPlayer. SoundPlayer and the system sounds have no volume of their own, which is why a scaled copy is used. One scaled copy per cue is cached for the current volume and dropped when the volume changes. Nothing is written to disk and the Windows volume is never touched.
      

      • At 0 percent nothing plays. If the cue's file cannot be found, is not plain PCM or cannot be read (for example the sound scheme has no sound for it), the cue stays silent rather than playing at full volume.
      

      Quiet hours
      

      Settings, Sounds and narration, Quiet hours: a switch and a daily window (QuietHoursStart, QuietHoursEnd, default 22:00 to 07:00, off by default). Inside the window no cue plays even when sounds are on.
      

      • Local clock; the start is included and the end is not. A start later than the end crosses midnight. Equal times mean no window. Unreadable times and a disabled switch never silence anything (QuietHours.IsQuiet).
      

      • Quiet hours silence cues only. Notifications, narration and every visible result are unchanged.
      

      • The settings page, the notification path (Notifier.SoundsEnabled) and ActionSounds.Emit all use the same quiet-hours and volume decision, so no caller can bypass it.
      

      Collapsible filters
      

      CollapseFilterState stores only collapsed surfaces in UserSettings.CollapsedFilters (at most 64 keys of at most 60 characters).
      

      • Every DataTable with filter chips has a chevron beside its search box (key table.<name>.filters). Collapsed, it shows "Filters · N on". The search box stays visible.
      

      • Storage statistics (storage.stats) and the Activity action filters (activity.actions) use CollapsibleBar.

      Workspace, navigation and command palette
      

      The application opens into a productive workspace in a frameless Material 3 window.
      

      Title bar
      

      • Application name (renamable in Settings, About), the running version and the updated-at time of that build, with seconds and the UTC offset. Both come from metadata compiled into the running executable; when it is missing the title bar says "provenance unavailable".
      

      • The command palette entry. Ctrl+Shift+F opens it from anywhere.
      

      • The engine context selector. It changes only which context this window uses; the global Docker context is never changed. The dot beside it is green when the engine answered a version check, red when it did not.
      

      • Notifications with an unread count, the accessibility tools menu, and minimize, maximize or restore, and close.
      

      Destinations and tabs
      

      The navigation rail lists Build, Creator, Images, Containers, Compose, Canvas, Storage, Monitor, System, Registry, Diagnostics, Tools, Activity and, at the bottom, Settings. Ctrl+1 to Ctrl+9 open the first nine.
      

      The first tab is the project workspace tab, named after the build folder. Rail navigation changes what the current tab shows and never adds tabs. New tab (Ctrl+T) opens a searchable catalog of every destination; choosing a destination that already has a tab focuses that tab instead of duplicating it. Tabs can be pinned, moved left or right, closed (Ctrl+W, middle click), and closed in bulk by text with a preview. Pinned tabs and the workspace tab are never closed in bulk. Open and pinned tabs are restored on the next start. Ctrl+Shift+A searches open tabs.
      

      Command palette
      

      The palette lists every command, destination and setting. Rows for settings contain the real control (for example the theme selector or the reduced motion switch), wired to the same setting as the Settings page. Enter runs the highlighted command, the arrow keys move, Escape closes. The palette has its own search with a regular expression mode and builder (Alt+R), and a persisted full-window size.
      

      Search everywhere
      

      Every list, table, menu, log and source viewer has its own search field. It matches plain text by default and has a .* regular expression toggle. The builder button next to the toggle, a right-click on the toggle, or Alt+R opens that field's own builder, which offers guided insertion, flags, an explanation tree, a bounded live test, a replace preview, a snippet library and saved patterns. Each search keeps its own state. See Search and the regular expression builder for the engine, the limits and the tab bulk close commands.
      

      Lists
      

      Tables support multi-select (click, Shift and Ctrl), select all matching, invert selection, a bulk action bar that states the exact count, row context menus with a filter field and their working shortcuts, filter chips, and export or copy of the visible rows as CSV, TSV, JSON, Markdown or HTML (see Records, exports, shortcuts and updates).
      

      Notifications
      

      Information and success messages appear as toasts in the bottom right corner and dismiss themselves. Warnings and errors stay until dismissed. The notification centre keeps dismissed messages with search, filters, copy and bulk dismiss. Modal dialogs are used only for real decisions.
      

      Destructive actions
      

      Removing data uses a two-key super confirmation: it names the action and every affected item, needs both keys before the slider unlocks, acts only when the slider reaches the end, and always offers Emergency exit and Escape.
      

      Operation panel
      

      Long operations stream their real output into the collapsible panel at the bottom (Ctrl+J) with elapsed time, a Cancel button and its own search. Only one foreground operation runs at a time. Cancellation is reported as cancellation, never as success.
